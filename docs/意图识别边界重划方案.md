# 意图识别边界重划方案（v2 草案 · 待拍板）

> 背景：闭卷口语评测（`eval/qa_closed_intent.py`，138 条）实测——规则层覆盖率 5.8%、精确率 0%；完整链路（规则+LLM 兜底）准确率 65.9%。根因不是 LLM 能力，是**七分类里「告警分析 / 故障诊断 / 缺陷分级」三个边界在口语里天然重叠**，加上评测集有重复、部分标注本身多义。

---

## 一、问题定位（用数据说话）

完整链路混淆矩阵（真值=行，预测=列）：

| 真值 \ 预测 | 问答 | 状态查询 | 告警分析 | 缺陷分级 | 故障诊断 | 工单生成 | 其他 |
|---|---|---|---|---|---|---|---|
| 问答(26) | 19 | 0 | 0 | 2 | 5 | 0 | 0 |
| 状态查询(26) | 0 | 26 | 0 | 0 | 0 | 0 | 0 |
| 告警分析(17) | 0 | 0 | 2 | 0 | **10** | 0 | 5 |
| 缺陷分级(17) | 0 | 0 | 0 | 7 | **7** | 0 | 3 |
| 故障诊断(17) | 0 | 0 | 0 | 0 | 12 | 0 | 5 |
| 工单生成(16) | 0 | 0 | 3 | 3 | 4 | 6 | 0 |
| 其他(19) | 0 | 0 | 0 | 0 | 0 | 0 | 19 |

三个结论：

1. **「故障诊断」是吸尘器**：把告警(10)和缺陷分级(7)全吸走了。这 17 条误判不是「判错」，是「三个类本来就是一个类」——口语里「跳闸了咋回事」既是告警又是诊断又是缺陷。
2. **状态查询 / 其他 100% 可分**，边界清晰，不需要动。
3. **工单生成 37.5%** 最惨，漏在「这个缺陷咋整，安排个人去处理」这类句子上——LLM 盯着「缺陷」当成了分析，忽略了「安排人」这个动作信号。

---

## 二、重划方案：七类 → 五类

把「告警分析 + 故障诊断 + 缺陷分级」合并为 **异常处置**，其余不动：

| 新意图 | 定义（可判定，不是含糊语义） | 判定特征 |
|---|---|---|
| **问答** | 问通用的规程/标准/依据/周期，**不指向某台具体设备此刻的异常** | 对象是「一类设备/一种操作」的通用做法 |
| **状态查询** | 问某台具体设备**此刻**的读数/状态 | 具体设备 + 「多少/几度/几伏/合着还是断着/啥情况」 |
| **异常处置** | 设备或事件出了异常，要分析原因 / 定级 / 处理 | 具体设备/事件 + 「咋回事/啥原因/要紧不/算哪级」 |
| **工单生成** | 明确的「安排人去处理」动作 | 处置动作词：安排人 / 派个活 / 开单 / 下单 / 去处理掉 |
| **其他** | 闲聊或与电网运维无关 | 无领域内容 |

**关键边界判定规则**（解决歧义的核心）：

- **问答 vs 异常处置**：看是否指向「具体设备此刻的异常」。「变压器渗油的处理规程是啥」→ 问答（通用知识）；「1号主变现在漏油了咋整」→ 异常处置（具体设备此刻）。
- **异常处置 vs 工单生成**：看有没有「安排人/派活」动作词。「这设备出啥问题了」→ 异常处置（只分析）；「这设备安排个人去检查处理」→ 工单（要派人）。

**为什么合并、而不是继续细分**：意图是软先验、不锁工具，ReAct 循环本来就会按证据动态选工具（先看有没有告警 ID → 告警分析；有没有缺陷描述 → 定级；否则 → 诊断）。在口语输入下，把「告警/诊断/缺陷」的区分责任交给循环里的工具调度，比交给一个前置分类器靠谱得多。

---

## 三、预期收益（按现有 138 条粗算）

| 口径 | 准确率 |
|---|---|
| 现状（7 类） | 65.9% (91/138) |
| 合并后（5 类） | **~78.3% (108/138)** |

+12.4pp，全部来自「告警→诊断(10) + 缺陷→诊断(7)」这 17 条从误判变成「异常处置→异常处置」正确。

合并后剩余误差（靠 few-shot + 重标评测集解决）：

- 问答 → 异常处置 7 条（「漏油了咋整」这类，标注本身有歧义，需重标）
- 异常处置 → 其他 13 条（LLM 把「这条提示啥意思」当成了闲聊，few-shot 能拉回）
- 工单 → 异常处置 10 条（漏看「安排人」动作词，few-shot 教）

## 四、待你拍板的问题

1. **是否接受合并成 5 类？** 这是最省事、收益最大的一步。若要保留 7 类，就得给三个重叠类写「可判定定义」，但口语里大概率还是分不开。
2. **「异常处置」内部要不要二级路由？** 建议不要——交给 ReAct 工具调度；若后续发现「定级」和「诊断」在工具选择上老走错，再考虑加二级。
3. **工单生成要不要拆成独立维度（动作维度）？** 建议先按平铺 5 类试；若 few-shot 后工单仍 <80%，再升级成「主题 × 动作」双标签。

## 五、带 few-shot 的兜底 prompt（配套代码草案）

```python
# app/engine/intent_router.py 中替换 route() 的 LLM 兜底部分

INTENTS_V2 = ["问答", "状态查询", "异常处置", "工单生成", "其他"]

INTENT_SYSTEM = (
    "你是电网运维意图分类器，把用户问题分为五类之一。\n"
    "各类定义（必须严格按定义判断，不要凭关键词字面）：\n"
    "- 问答：问通用的规程/标准/依据/周期，不指向某台具体设备此刻的异常。\n"
    "- 状态查询：问某台具体设备此刻的读数/状态（多少度/几伏/合着还是断着/啥情况）。\n"
    "- 异常处置：设备或事件出了异常，要分析原因、定级或处理（咋回事/啥原因/要紧不/算哪级）。\n"
    "- 工单生成：明确要安排人去处理（安排人/派个活/开单/下单/去处理掉）。\n"
    "- 其他：闲聊或与电网运维无关。\n"
    "只输出 JSON：{\"intent\":\"...\",\"confidence\":0.x}"
)

FEWSHOT: list[tuple[str, str]] = [
    ("变压器渗油的处理规程是什么", "问答"),
    ("断路器多久检修一次", "问答"),
    ("1号主变现在多少度", "状态查询"),
    ("母线电压现在多少", "状态查询"),
    ("1号主变漏油了，咋回事", "异常处置"),
    ("主变差动保护跳了，帮我瞅瞅", "异常处置"),
    ("这设备的毛病算哪一档", "异常处置"),
    ("帮我在系统里开个单，安排人去处理", "工单生成"),
    ("这个缺陷派个活，让人去修", "工单生成"),
    ("今天天气怎么样", "其他"),
]

def _llm_intent(self, text: str) -> tuple[str, float] | None:
    messages = [{"role": "system", "content": INTENT_SYSTEM}]
    for q, a in FEWSHOT:
        messages.append({"role": "user", "content": q})
        messages.append({"role": "assistant", "content": a})
    messages.append({"role": "user", "content": text})
    try:
        out = self.llm.chat_json(messages)
        intent = out.get("intent")
        if intent in INTENTS_V2:
            return intent, float(out.get("confidence", 0.5))
    except LLMError:
        pass
    return None
```

**规则层配合改动**（与合并对应）：`RULES` 里「告警分析/缺陷分级/故障诊断」三行合并成一行「异常处置」，并把「缺陷/告警」这类宽泛词从关键词里删掉（它们单字命中不了意图，只会以 0.9 置信抢跑）。建议规则层只保留强动作词：

```python
RULES = [
    ("工单生成", ["工单", "派单", "开单"]),
    ("状态查询", ["温度", "电流", "电压", "台账", "多少度", "几伏"]),
    ("异常处置", []),   # 口语下无高精确关键词，直接走 LLM 兜底
    ("问答", ["规程", "依据", "规定", "标准"]),
]
```
