# 电网智能运维 Agent 前端工作台设计

> 目标：把现有的单页 Demo（`web/index.html`）升级为一个可日常使用的运维工作台。
> 设计思路借鉴「企业级研发与运维 Agent 平台前端设计 PRD」的工程控制台哲学（可观测、可审批、可评测、权限表现、非聊天玩具），映射到电网设备运维场景，对接已有后端接口。

---

## 1. 文档信息

| 项 | 内容 |
|---|---|
| 前端定位 | 面向运维值班人员与平台管理员的 Agent 运维工作台 |
| 目标用户 | 运维人员、设备专责、管理员 |
| 核心任务 | 提交诊断/定级任务、查看运行链路、确认工单、管理知识库、审核复盘案例、查看系统健康 |
| 设计形态 | 桌面优先的运维控制台（非移动优先） |
| 技术栈 | **React + TypeScript + Vite**（已定） |

---

## 2. 设计原则（借鉴 PRD，适配本场景）

1. **首屏是工作台，不是聊天框**——用户进来就能选设备、提任务；
2. **信息密度高，每个区块只服务一个判断**——避免营销式卡片堆叠；
3. **所有 Agent 结论必须能追溯到证据**——对话/诊断结果要展示来源（对应后端的证据溯源能力）；
4. **写操作先看到风险、参数、影响面，再确认**——工单落库走二次确认（后端已有，前端要呈现清楚）；
5. **链路默认看摘要、细节按需展开**——运行链路页不要一上来铺满 JSON；
6. **权限在前端只是体验，后端才是边界**——按钮显隐按角色，但安全靠后端 `require_role`。

## 3. 用户角色与权限表现

后端已有 4 角色（`app/core/auth.py`），前端做镜像显隐：

| 角色 | 能看/能做 | 禁用 |
|---|---|---|
| operator（运维） | 对话、诊断、缺陷评估、出工单草稿 | 审核复盘案例、看运行链路、看 metrics |
| monitor（监控） | 只读浏览告警/设备/知识库 | 写操作 |
| manager（管理） | 审核复盘案例、确认工单、看历史 | 管理用户 |
| admin（管理员） | 全部：运行链路、metrics、用户管理 | 无 |

前端要求：无权限的按钮**禁用并显示原因**（如「需要 admin 权限」），而不是隐藏后让用户以为没这功能。

## 6. 核心页面设计

### 6.1 对话工作台（P0，核心）

现有聊天已具备：SSE 流式、意图、工具调用、证据、确认框。按 PRD 思路增强为「任务型工作台」：

- 顶部：设备选择（复用现有设备选择器）+ 意图提示；
- 中部：对话流（保留现有 SSE 事件渲染：`intent`/`tool_call`/`degraded`/`clarify`/`confirm_required`/`final_answer`）；
- 证据展示：`final_answer` 的 `sources`、`verification` 字段要可视化（来源列表 + 溯源通过/问题标记）；
- 确认框：工单草稿确认（现有 `confirm_required`），补充展示草稿的**等级、设备、消缺时限**，而不只是 JSON。

### 6.2 运行链路详情（P0）

后端 `/traces/{session_id}` 已返回步骤（tool、params、result、elapsed_ms、degraded）。前端做**时间线可视化**：

- 每步一行：步骤号 + 工具名 + 耗时 + 降级标记（badge）；
- 点击展开：参数、结果、来源；
- 顶部：会话摘要（意图、总步骤、总耗时）；
- 关联：从对话工作台「查看本次链路」按钮跳转过来。

### 6.3 工单管理 + 确认（P0）

- 列表页：工单状态（草稿/已下发）、等级、设备、消缺时限；
- 确认动作：对话里确认（现有）之外，工单列表里也能对「草稿」操作确认/取消（已有 `POST /workorders` 落库草稿 + `POST /workorders/{order_id}/confirm`、`/cancel`，限 manager/admin）。

### 6.4 设备管理（P0）

- 列表：设备名称、类型、电压等级、站所、状态；
- 详情：台账 + 量测（`/devices/{id}/measurements`）+ 状态四态（`/devices/{id}/state`）+ 告警（`/alarms`）。

### 6.5 复盘案例（P1）

现有「复盘案例」tab 已有基础版（列表 + 通过/驳回/废止 + 检索），工作台化时迁移过来，补：状态过滤、检索高亮、审核需 manager/admin 的禁用态。

### 6.6 评估看板（P2，需补后端）

对应我们已有的 eval 脚本（Recall@K、定级压测）。前端展示：检索 Recall@5/10、定级命中率/误判率、失败分类。后端已有 `GET /evals/summary`（读 `eval_run` 表各套件最新结果）与 `GET /evals/runs`（历史，admin）；脚本跑完用 `scripts/publish_eval_result.py` 落库。

## 7. 前端数据模型（对齐后端返回）

后端统一返回 `{code, message, data}`，前端主要消费：

```ts
// 对话最终答案
type FinalAnswer = {
  type: "final_answer";
  answer: string;
  sources: string[];
  verification?: { passed: boolean; issues: string[] };
  budget?: { requests: number; charged_tokens: number };
};
// 运行链路步骤
type TraceStep = {
  step: number; tool: string; params: object; result: object;
  sources: string[]; elapsed_ms: number; degraded: boolean;
};
// 设备
type Device = {
  device_id: string; device_name: string; device_type: string;
  voltage_level: string; station: string; status: string;
};
```

## 8. 状态与反馈

| 状态 | 设计 |
|---|---|
| Loading | 骨架屏，不用整页 spinner |
| Empty | 给下一步操作（如「先去对话工作台出个工单」） |
| Error | 可行动错误（重试 / 查看健康页） |
| 权限不足 | 显示当前角色 + 所需角色 |
| 待确认 | 明确「动作不会执行，除非你确认」 |

## 9. 验收标准

**P0 验收**：能登录 → 选设备 → 对话诊断（看到意图/工具/证据/结论）→ 出工单草稿 → 确认落库 → 在工单列表看到；能从对话跳转运行链路看时间线；缺陷分级能在缺陷页评估。

**P1 验收**：知识库检索、复盘案例审核（manager 能过、operator 看不到按钮）、系统健康、metrics（admin）可用。

**权限验收**：operator 登录看不到「审核」按钮、访问 `/metrics` 返回 403。

## 11. 技术栈决策（已定：React + TypeScript + Vite）

| 项 | 选型 | 说明 |
|---|---|---|
| 框架 | React 18 + TypeScript | 与参考 PRD 一致，复用其组件/数据模型设计 |
| 构建 | Vite | 开发快、开箱即用 |
| 路由 | React Router | 页面清单见第 4 节 |
| 状态/数据 | TanStack Query + Zustand | 服务端状态用 Query（缓存/重试/加载态），轻量 UI 状态用 Zustand |
| UI 组件 | Ant Design 或 shadcn/ui | 中文工程控制台场景 Ant Design 成熟；偏好无头组件可走 shadcn/ui |
| 样式 | CSS Variables（复用现有 `--accent:#2563eb` 等 token） | 保持视觉一致 |
| 链路可视化 | React Flow | 运行链路时间线（第 6.2 节） |
| SSE | 原生 fetch + ReadableStream | 复用现有 `index.html` 的 SSE 事件处理逻辑 |

> 与现有 `web/index.html` 的关系：**用框架重写**，替换掉原生 JS 单页。现有单页里的 SSE 事件处理逻辑、配色 token 保留迁移过去。
