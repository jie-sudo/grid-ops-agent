# 历史数据保留与复盘案例库设计

> 回答「投入生产 3 年后，用户怎么知道 3 年前的东西」。
> 现状：`Message` / `Trace` / `EvidenceRecord` / `BudgetRecord` 只增不删，无分区无归档无日期检索；
> Agent 不会从历史处置里学东西（`SessionSummary` 表预留未用）。本设计补齐三层能力。

## 0. 结论速览

「3 年后知道」靠三层，缺一不可：

1. **留痕可翻**：原始流水全量落库 + 分区/归档 + 日期检索（让人能回看）。
2. **经验可复用**：从已关闭工单/诊断沉淀出「复盘案例」，人工审核后进案例库（让 Agent 能复用）。
3. **旧不误导新**：所有知识带版本 + 有效期 + 废止链（让 3 年前的过期东西不误导现在）。

分期：**P0 = 第 1 层**（地基，先做）；**P1 = 第 2 + 3 层**（案例库 + 治理）。

---

## 1. P0 —— 历史留痕的保留与检索

### 1.1 问题
`Message` / `Trace` / `EvidenceRecord` / `BudgetRecord` 无限增长，3 年即百万级行：
查询变慢、存储膨胀、且没有按日期检索的入口。

### 1.2 方案：索引 + 归档 + 日期检索（先不引入真分区）

| 动作 | 内容 |
| --- | --- |
| 索引 | 四张流水表统一在 `created_at` 上建索引（`Message` / `Trace` / `EvidenceRecord` / `BudgetRecord`） |
| 归档 | 新增配置 `history_retention_months`（默认 36）+ `history_archive`（默认 true=归档保留） |
| 清理 | `scripts/archive_history.py`：把超过热区月数的行挪到 `*_archive` 归档表（结构同源），再删热区；可挂定时/每日启动执行 |
| 检索 | 历史查询接口统一支持 `start` / `end`（ISO 时间）+ `limit` / `offset` 分页 |

> 为什么先不做真分区：声明式分区（`PARTITION BY RANGE`）对 3 年流水是正解，但对当前 demo 规模
> 收益低、运维成本高（新分区要提前建）。归档表方案更简单、可回退，将来数据量真上去了再迁移分区。

### 1.3 归档表
`message_archive` / `trace_archive` / `evidence_record_archive` / `budget_record_archive`，
结构与热表一致，仅追加写入、不参与业务查询。归档后热表只保留近 N 个月。

### 1.4 历史查询接口（扩展 + 新增）
- `GET /api/v1/sessions` 加 `start/end/user_id/limit/offset`（现有仅 `limit`）
- `GET /api/v1/workorders` 加 `start/end/level/device_id/limit/offset`
- `GET /api/v1/defects` 加 `start/end/level/device_id/limit/offset`
- `GET /api/v1/traces/{session_id}` 加 `start/end`
- 新增 `GET /api/v1/messages?session_id=&start=&end=&limit=&offset=`

## 2. P1 —— 复盘案例库（长期记忆）

### 2.1 目标
让 Agent 排查时能检索「3 年里处理过的相似缺陷/诊断」，而不是翻 3 年原始流水。

### 2.2 数据模型：新增 `ReviewCase`

```
review_case
├─ case_id         String(32) PK  业务编号
├─ title           String(128)
├─ device_type     String(32) idx 变压器/开关柜/电缆/通用
├─ symptom         String(512)    现象描述（检索主键）
├─ root_cause      String(512)    根因（可空，待核实时为空）
├─ action          String(1024)   处置措施
├─ basis_refs      JSON           依据：知识出处/证据ID/工单ID（可追溯）
├─ source_type     String(16)     工单/诊断/人工
├─ source_ref_id   String(32)     关联工单/缺陷ID
├─ session_id      String(64)     来源会话
├─ status          String(16) idx 草稿/已审核/已废止
├─ version         String(16)     1.0.0（与知识库同构）
├─ effective_date  DateTime      生效时间
├─ superseded_by   String(32)     废止链（指向新案例）
├─ reviewer / reviewed_at / created_at / updated_at
```

状态机：`草稿 → 已审核 → 已废止`（废止填 `superseded_by`，与规程的 `status/superseded_by` 同一套治理）。

### 2.3 沉淀流程（规则提炼，不用 LLM，符合 C1）

**触发点**：工单二次确认落库成功后（`_handle_confirm` confirmed 分支）。

**提炼方式**：确定性规则，从「工单字段 + 会话内最近一次 diagnose/query_state 的 trace 结果」映射：
- `symptom` = 工单 content 或诊断 fault_type
- `device_type` = 工单 ref_id 对应设备类型
- `action` = 工单 content 的处置部分
- `root_cause` = 诊断 fault_type（若 diagnose 未命中则置空 → 待核实）
- `basis_refs` = 诊断 basis / 知识出处
- `source_ref_id` = 工单 order_id

生成 `status=草稿`，**默认不可检索**。

### 2.4 人工审核
- `POST /api/v1/review-cases/{id}/approve`（角色：manager/admin）→ `已审核`
- `POST /api/v1/review-cases/{id}/reject` → 删除或标记废弃
- `POST /api/v1/review-cases/{id}/supersede`（带 `superseded_by` + 新 version）→ 旧案例废止

### 2.5 Agent 检索（复用）
- 新增只读工具 `search_review_cases(query, device_type)`：结构化过滤 + 关键词检索
  （与现有知识库一致，先不做向量；`status=已审核` 且未废止的当前版本才返回）。
- 接入 `react_loop` 工具注册表 + `SYSTEM_PROMPT` 提示（诊断/告警分析意图时可先查案例）。

### 2.6 版本/时效治理（第 3 层）
- `ReviewCase` 带 `version / effective_date / superseded_by / status`，检索默认过滤 `status=已废止`。
- 与知识库（`KnowledgeDoc` + ChromaDB 的 `status/superseded_by`）治理同构，一条规则管两类知识。

---

## 3. 待确认的决策点

1. **案例提炼方式**：推荐「确定性规则」（符合 C1，成本低、可审）；是否要 LLM 提炼增强？
2. **分期顺序**：P0 先做（历史保留+查询），P1 后做（案例库）？还是一次全做？
3. **归档策略**：`history_retention_months` 默认 36、超期**归档保留**（`history_archive=true`）还是直接删除？
4. **案例检索**：先关键词（与知识库一致），向量检索留到以后？还是这次直接上 ChromaDB 第二 collection？

## 4. 交付清单（实现阶段）

- P0：models 加归档表 + created_at 索引；config 加保留策略；`scripts/archive_history.py`；API 扩展日期/分页。
- P1：models 加 `ReviewCase`；`app/skills/review_case.py`（规则提炼）；审核 API；`search_review_cases` 工具；react_loop 接入；前端 `web/index.html` 加「复盘案例」tab（列表 / 检索 / 通过-驳回-废止按钮，按角色显隐）；单测（纯逻辑：提炼规则 + 版本过滤）。
